# agent-fastpath v0.1.1 Public Release Design

## Goal

Publish `agent-fastpath` v0.1.1 as a trustworthy open-source patch release that fixes FP1–FP6, passes every automated release gate, and exposes enough source, tests, documentation, and benchmark methodology for users to verify its claims without exposing credentials, machine-specific data, or private-repository content.

## Release scope

The release is a patch release, not a redesign. It includes the FP1–FP6 corrections already present on `main`, the subsequent confidence-calibration corrections on local `HEAD`, the TypeScript compile correction required by the release gate, complete regression coverage for the exact benchmark probes, and public-project hygiene.

The npm package remains intentionally small: compiled CLI, README, license, and package metadata. Source, tests, CI, documentation, and benchmark code live in the public GitHub repository and are not copied into the runtime package.

## Public/private boundary

Public repository content:

- All runtime source under `packages/`.
- Unit, integration, smoke, browser, and live-release tests.
- Benchmark source and sanitized methodology/results.
- Architecture, configuration, provider, security, and benchmarking documentation.
- CI and npm release workflows.
- `SECURITY.md`, `CONTRIBUTING.md`, changelog/release notes, license, and README.

Local-only content:

- `.env` and every real API key or credential.
- `node_modules`, built `dist` output, tarballs, caches, and temporary files.
- Raw benchmark JSON or Markdown containing absolute paths, private repository names, source snippets, local usernames, or unpublished code findings.
- Personal notes and machine-specific MCP configuration.

Synthetic credentials used solely to prove redaction remain public test fixtures. Their construction must make it obvious that they are nonfunctional.

## Correctness work

1. Remove the unreachable `res.status === "escalate"` comparison in browser claim handling so TypeScript compilation succeeds without changing runtime behavior.
2. Add or strengthen regression tests using the exact FP1–FP6 benchmark inputs:
   - five benign FP1 states must not be blocked by `DETERMINISTIC_TEST_FAILURE_DETECTED`;
   - deterministic BLOCKED and HIGH_RISK mappings must use safe status/action pairs;
   - browser semantic checks must accept two supported claims and reject the negative claim;
   - browser traces must be immediately retrievable with URL/mode diagnostics;
   - token accounting must stay bounded by parsed observations;
   - a diff plus green tests must use `semantic_jev`, never deterministic auto-pass.
3. Preserve existing behavior where a semantic provider may independently block a state after deterministic fall-through; the FP1 regression specifically prohibits the incorrect deterministic rule.

## Open-source documentation

- `SECURITY.md` documents supported versions, private reporting, the TypeSafe data boundary, browser/SSRF protections, irreversible-action constraints, secret redaction, and non-goals.
- `CONTRIBUTING.md` documents setup, tests, browser installation, deterministic-versus-semantic test expectations, coding conventions, and pull-request requirements.
- `CHANGELOG.md` records v0.1.1 as a corrective release and names FP1–FP6 in user-facing language.
- README and security documentation explicitly state that semantic evaluation sends redacted state or bounded file excerpts to the configured TypeSafe provider. Path triage keeps full files out of the MCP host context but is not a local-only semantic operation.

## Versioning and publication

- Set the root workspace and publishable CLI package versions to `0.1.1`, updating the lockfile consistently.
- Do not move or recreate `v0.1.0`.
- Commit and push all release changes to `main` before tagging.
- Create `v0.1.1` only from a clean commit for which CI passes on Node 20, 22, and 24.
- Let `.github/workflows/release.yml` perform the npm publication with provenance.

## Verification gates

The release candidate is acceptable only when all of these pass from a clean working tree:

1. `npm run typecheck`.
2. `npm test`, including real Chromium tests against local fixtures.
3. `npm run build`.
4. Built CLI smoke tests.
5. `npm pack --dry-run --json --workspace packages/cli` shows only the intended runtime files and version 0.1.1.
6. A tracked-file secret and absolute-path scan finds no real secrets or private machine paths.
7. Production live scenarios pass with an explicitly supplied TypeSafe key. Live repository triage must use this public repository only; it must not include private repositories.
8. The installed tarball, not only the source checkout, passes the exact FP1–FP6 release probes.

If the TypeSafe service or public network is unavailable, publication remains blocked rather than treating mock-provider results as production verification.

## Error handling and release safety

- A failed typecheck, test, build, smoke test, package inspection, secret scan, or live scenario blocks tagging.
- Publishing is performed only by the existing tag-triggered workflow; no manual `npm publish` fallback is used.
- Release notes must distinguish deterministic guarantees from semantic-provider behavior and must not advertise mock-provider calibration as production accuracy.
